# [YANGA-013] pytest test framework: test a component, an integration component or a variant through a shared library

## Summary

As a developer on a yanga product line, I want to test a component, an integration component or a variant with pytest against a shared library built from it, so that I can write C tests in Python and see their results and coverage in the yanga reports, as I do for gtest today.

## Description

yanga tests a component or a variant only from C++, through the `gtest` testing block. The schema already allows one block per framework, but only `GTestCMakeGenerator` reads a block. SPLedY drives its Disco variant from pytest by hand: a platform with a small C API, a hand-written ctypes binding and a fixture that builds the library; that test has no JUnit file, no coverage and no report entry.

## What exists

- [src/yanga/cmake/gtest.py](../../src/yanga/cmake/gtest.py): block selection, object library with `--coverage`, partial link, the `clanguru mock` call, the run with `|| true`, JUnit as `TestResultFile`, gcovr coverage, the variant test with `GCOV_PREFIX`, integration components.
- [src/yanga/cmake/create_shared_library.py](../../src/yanga/cmake/create_shared_library.py): the product shared library (no `lib` prefix, `WINDOWS_EXPORT_ALL_SYMBOLS ON`).
- [docs/reference/product.md](../reference/product.md) (testing blocks), [docs/reference/cmake.md](../reference/cmake.md), [docs/how-to/add-component-tests.md](../how-to/add-component-tests.md), [docs/explanation/concepts.md](../explanation/concepts.md).
- yanga-core: `TestingBlockConfig` in `src/yanga_core/domain/config.py`, integration components in `src/yanga_core/domain/component_resolver.py`.
- clanguru `bind` (CLG-019). SPLedY `platforms/pc_gui/spled_lib.py` and `test/test_Disco.py`: the hand-made variant test this replaces.

## Scope decisions

- **Three test scopes: component, integration component and variant.** The framework is for any of them, and SPLedY starts with one or two tests per scope. An integration component (one with `integrates:`) already compiles the sources of the components it integrates, so yanga-core does not change.
- **Missing functions are mocked in Python.** For every function a test scope calls but does not define, a generated C function (a trampoline) forwards the call to a Python callable the test sets, for example a `unittest.mock.Mock`. Hand-written C fakes in `mockup_sources` stay possible for any function a trampoline cannot forward. Rejected: gmock mocks with their default action, because Python cannot set them; generated C stubs with counters and return values, because every hard case (a value per call, out-parameters, callbacks) would need its own C design, which `unittest.mock` already gives in Python.
- **clanguru generates the Python binding and the Python mocks, with the templates in clanguru.** A shared library holds no types, so the declarations come from the C sources; clanguru already parses them with the project's compile database. The templates belong to clanguru, like the gmock templates, because anyone who needs a Python binding for C code can use them, not only yanga. Rejected: hand-written bindings (as SPLedY's `spled_lib.py`), third-party generators (ctypesgen, cffi), and templates shipped by yanga.
- **`bind` chooses symbols exactly as `mock` does,** with the same code: every undefined symbol whose declaration clanguru finds, minus the `--exclude-symbol-pattern` matches. In strict mode `bind` fails only when an undefined symbol has no declaration, because the library cannot link then; unsupported types never fail and go to the log; a defined symbol without a declaration (for example from `mockup_sources`) is left out of the binding and listed in the log. The `bind` docs state these rules. Rejected: `mock`'s strict check, which also fails on unsupported types and so contradicts the log. Today this is split between `main.py` (the `nm` call) and `MocksGenerator.generate` (patterns, declarations); it moves into one function both commands call. That function does the selection; each command keeps its own strict check. `bind` requires `--partial-object-file`, since it has no `--symbol`. Choosing the defined symbols for the binding is new code in that function, with the same patterns and declaration lookup. Rejected: own selection rules for `bind`, because the two commands would then mock different things for the same code. A filter by project folder does not exist in `mock` today and is not added here.
- **C types in the first version.** Functions and variables with scalar, pointer, struct and enum types. Not yet: function pointers, unions, bit fields, variadic functions, and functions that return a struct by value, because a `ctypes` callback cannot return a struct. A function with an unsupported type gets no Python mock and is listed in the log; the user writes a C fake in `mockup_sources`, or the link fails and names it. The test library links with `-Wl,-z,defs` on Linux, which otherwise accepts missing symbols and fails only when the library is loaded.
- **A call with no Python mock set** returns a zero-initialised value of the return type and is recorded; the binding offers the list as `lib.mocks.unexpected_calls`. A test checks it if it wants. Rejected: failing the test automatically, because that needs a pytest plugin.
- **The test imports the binding; the binding loads the library next to it.** yanga writes the test library and the binding into the test scope's build folder and puts that folder on `PYTHONPATH` when it runs pytest. Rejected: an environment variable with the library path, which the binding makes unnecessary, and a pytest plugin with a fixture, which needs an installed package and gives nothing more today.
- **An integration component's test library** holds its own sources and the integrated ones, with coverage, and Python mocks for what is still missing. Its coverage counts as integration coverage, apart from unit coverage, as for gtest.
- **The variant scope** links the same components as the gtest variant test (no containers, no integration components), in the variant's `variant_test` folder; its files are named `<variant>_pytest` and `<variant>_binding`, and it writes its gcov data to its own `GCOV_PREFIX` folder.
- **Operating systems.** The pytest generator supports the same systems and toolchains as the gtest generator. Risk, checked first: gcov writes its data at process exit; for a library loaded through ctypes this must happen at the end of the pytest process, on every system. yanga's CI runs on Ubuntu and Windows; on macOS the human runs the check once by hand. Rejected: a macOS runner in yanga's CI for this one check.
- **File names in the test scope's build folder.** For the test scope `light_controller`, yanga calls `clanguru bind --filename light_controller_binding --library-name light_controller_pytest`. The folder holds `light_controller_pytest.dylib` (`.so`, `.dll`), `light_controller_binding.py`, `light_controller_binding_mocks.c` and `light_controller_pytest_junit.xml`. The `_binding` suffix keeps the module name apart from any test file or component name.
- **New words, where they are defined.** No repository has a glossary file. *Test scope* and *test library* are yanga's words and go into yanga's `docs/explanation/concepts.md`. *Binding* and *Python mock* are clanguru's words and go into the `bind` section of clanguru's `docs/features/index.md`. Drafts are in the folder of the item that adds the word and land with its implementation.
- **ctypes.** The binding and the Python mocks use `ctypes` from the standard library. Rejected: cffi and a compiled extension, because they need a second compiler setup; SPLedY already uses ctypes.
- **An own test library per scope.** yanga builds a shared library for each test scope, with `--coverage` and the Python mocks, as gtest builds its own executable. Rejected: loading the product library of `CreateSharedLibraryCMakeGenerator`, because it must carry neither coverage nor mocks.
- **pytest builds its own object libraries** for every test scope, `<name>_pytest_PC_lib` and the partial-link object `<name>_pytest_PC.o`, next to gtest's in the same build folder; the `mockup_sources` objects go into `<name>_pytest_PC.o` as gtest does. Rejected: linking gtest's `<name>_PC_lib`, because pytest must work on a platform without the gtest generator.
- **A collector generator, `TestResultsCMakeGenerator` (module `yanga.cmake.test_results`).** A platform lists it after its test generators. It creates the phony `<name>_test`, `<name>_coverage` and `<name>_report` targets, merges the coverage tracefiles per entry, and writes the Coverage pages and the merged coverage pages. The test generators only build, run and register. Rejected: gtest collecting for every framework, because pytest would then define the same targets again, gtest merges before a generator listed after it has registered anything, and pytest must work without gtest; `SphinxTestReportCMakeGenerator` collecting, because its job is the results report and a platform without it would lose its coverage; gtest collecting only when no collector is listed, because that is two code paths for one job. This breaks platforms that test: they must list the new generator. Accepted, because yanga-core is at 0.x and yanga is in alpha.
- **Compiler for the tests.** clanguru and yanga install clang with a `PoksInstall` step (`pypeline.steps.poks_install`) in their `pypeline.yaml`, from the same poks bucket as SPLedY's `poks.json`, and their tests that build C use it; no test is skipped for a missing compiler. The step runs in CI: clanguru's `.github/workflows/ci.yml` lists it and requires `pypeline-runner>=1.28`, where `PoksInstall` exists; yanga puts it into `pipeline/test.yaml`, which its CI runs. yanga's gcov check also runs with gcc on Ubuntu, because SPLedY's gtest platform builds with gcc.
- **pytest runs in the interpreter that runs yanga.** pytest is a dependency of the project, not of yanga. yanga checks for pytest when it generates the build files and stops with a message that names pytest; it writes `<python> -m pytest` with the interpreter it runs in. pytest runs in the project folder, with the test files given by path and `-p no:cacheprovider`.
- **The pytest block's mocking config has gtest's shape and merge rule.** `config.mocking.strict` and `config.mocking.exclude_symbol_patterns`, on the block and on the platform's generator config, the block's values over the platform's; they are passed to `clanguru bind`. It reuses yanga-core's `MockingConfig`; `enabled: false` is an error that names the field, because pytest always needs the mocks. Rejected: one mocking entry shared with gtest, because pytest would then read gtest's settings and break on a platform without the gtest generator.
- **Generator order.** A platform lists the pytest generator after the gtest generator and before `TestResultsCMakeGenerator`, `SphinxTestReportCMakeGenerator` and `ReportCMakeGenerator`, which read what it registers.
- **A failing test does not fail the build,** as with gtest. The result is in the JUnit file and the report.
- **Order and release.** clanguru `bind` first, released. YANGA-012 in parallel, as it does not need clanguru. Then the yanga pytest generator, blocked by both. Then SPLedY, with editable installs of clanguru and yanga, before the yanga release; yanga is released only when SPLedY is green.

## What users see

- **New generator `PytestCMakeGenerator` (module `yanga.cmake.pytest`)**, listed by a platform like any generator. It reads the `framework: pytest` block of a component, an integration component and a variant: `sources`, `mockup_sources`, and `config.mocking.strict` and `config.mocking.exclude_symbol_patterns`, also on the platform's generator config. Not breaking: the schema already allows the block; no existing key changes. UAT: yes. Why: `GTestCMakeGenerator` reads only `gtest` blocks. Approved by the human (2026-11-24)
- **Files in the test scope's build folder**: `<scope>_pytest.<dll|so|dylib>`, `<scope>_binding.py` (the import name a test uses), `<scope>_binding_mocks.c`, `<scope>_pytest_junit.xml`. Not breaking: new. UAT: yes, a test imports `<scope>_binding`. Why: the test needs a stable import name. Approved by the human (2026-11-24)
- **pytest is required in the project's environment** when a platform lists the pytest generator; without it yanga stops when it generates the build files, with a message that names pytest. Not breaking: only for projects that opt in. UAT: no. Why: yanga runs pytest in its own interpreter and does not depend on pytest itself. Approved by the human (2026-11-24)
- **Domain terms *test scope* and *test library*** in `docs/explanation/concepts.md`. Not breaking. UAT: no. Why: new concepts with no word yet. Approved by the human (2026-11-24)

## Out of scope
